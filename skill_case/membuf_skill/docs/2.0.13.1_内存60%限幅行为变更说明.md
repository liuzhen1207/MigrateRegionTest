# 【2.0.13.1】存储引擎/写入内存 60% 限幅的行为变更说明

> 提出人：刘珍（测试）
> 日期：2026-11-10
> 关联需求：**TDB-330**「新增数据库风险模式 dangerous_mode=false/true」（负责人 江天，验证 肖志红，迭代 V2.0.13.1，P0）
> 需求分析/评审文档：[docs/359 V2.0.13.1-其他模块-配置管理-数据库风险模式-需求分析](https://plm.infra.timecho.com/docs/359)（高宏志，2026-09-16，V0.1）
> 发现方式：内存缓冲区专项回归（membuf_skill）用例 **MB-02** 在 2.0.13.1 RC1 上失败

---

## 一、结论先说

**这是 TDB-330 有意引入的新行为，不是缺陷。**
但它是**用户可感知的容量变化**，请研发确认是否需要体现在**发版说明**里。

---

## 二、行为变化

### 2.1 变更点

| | 2.0.12.1 | **2.0.13.1** |
|---|---|---|
| `dangerous_mode` 参数 | **不存在** | **新增**，默认 `false` |
| storage 占比 > 60% 时 | 按 `datanode_memory_proportion` 原样分配 | **强制压到 maxMemory × 60%**，并打印 WARN |

### 2.2 代码位置

`iotdb-core/datanode/src/main/java/org/apache/iotdb/db/conf/DataNodeMemoryConfig.java`

```java
private static final int SAFE_STORAGE_ENGINE_MEMORY_NUMERATOR = 3;
private static final int SAFE_STORAGE_ENGINE_MEMORY_DENOMINATOR = 5;   // 60%
private static final String DANGEROUS_MODE = "dangerous_mode";

private static boolean isStorageEngineMemoryCapped(properties, proportions) {
  return !Boolean.parseBoolean(properties.getProperty(DANGEROUS_MODE, "false").trim())
      && proportions.values[STORAGE_ENGINE_MEMORY_INDEX] * 5 > proportions.sum * 3;
}

private static long calculateStorageEngineMemorySizeInBytes(...) {
  if (isStorageEngineMemoryCapped(properties, proportions)) {
    LOGGER.warn("... exceeds 60% while dangerous_mode is false. "
              + "The allocated StorageEngine memory is limited to 60% of the DataNode heap. "
              + "Configured value: {}.", memoryAllocateProportion);
    return calculateProportionalMemorySize(maxMemoryAvailable, 3, 5);
  }
  return calculateProportionalMemorySize(maxMemoryAvailable, proportions.values[0], proportions.sum);
}
```

判据：`storage 占比 × 5 > 总占比 × 3` ⇔ **storage 占比 > 60%**。

## 三、实测数据（2.0.13.1 RC1，Build ab6d3de）

用例 MB-02 配置 `datanode_memory_proportion=9:1:1:1:1:1`（storage = 9/14 = **64.3%**）。

| 观测项 | 期望（旧行为） | **实际（2.0.13.1）** |
|---|---|---|
| `allocateMemoryForWrite`（5 个 DN 全部一致） | maxMemory × 9/14 = **9669716208**（约 9.0 GiB） | **8058096844**（约 7.5 GiB） |
| 限幅告警 | **不应出现** | **出现 1 次** |
| 反推 maxMemory | — | 15041780768（约 14 GiB） |

即：配置 9:1:1:1:1:1 的用户，**写入内存实际比按比例分配少了约 1.5 GiB**。

DN 日志告警原文：
```
The StorageEngine proportion in datanode_memory_proportion exceeds 60% while
dangerous_mode is false. The allocated StorageEngine memory is limited to 60%
of the DataNode heap. Configured value: 9:1:1:1:1:1.
```

## 五、评审文档（docs/359）已明确的内容

| 项 | 评审文档结论 |
|---|---|
| 模型 | 通用 / **企业版** |
| 使用人员 | **内部** |
| **是否需要更新用户手册** | **否** |
| 兼容性要求 | 升级前已将 StorageEngine 占比配置为超过 60% 的用户，**需修改内存比例，或显式配置 `dangerous_mode=true`** |
| 默认值 | `dangerous_mode` 默认**关闭**（false） |

评审文档对"限幅"的设计初衷写得很清楚：
> 原有逻辑会按比例直接分配内存，未限制 StorageEngine 的最大占比。用户可将第一项调得过高，例如 8:1:1:1:1:1，使 StorageEngine 占比超过 60%。因此，本需求在原有内存比例配置前增加一层风险保护。

**所以"写入内存被压到 60%"是预期行为，不是缺陷。**

## 六、需要研发确认的问题（基于评审文档修订）

### 6.1 【重要】设计说"失败"，实现是"限幅并告警"——两者是否一致？

评审文档"4. 自测及测试场景建议"写的是：

> - 默认关闭风险模式：StorageEngine 占比**等于 60% 时通过，超过 60% 时失败**。
> - 开启风险模式后，StorageEngine 占比超过 60% 时通过。

而实际实现（`DataNodeMemoryConfig.calculateStorageEngineMemorySizeInBytes`）是：

- **不报错、不阻止启动**
- 把 StorageEngine 内存**静默压到 maxMemory × 60%**
- 只打印一条 **WARN**

**请确认预期语义**：
- (a) "失败"仅指"配置值不被采纳（被限幅）"，当前实现正确；或
- (b) "失败"指启动应**报错退出**，当前实现与设计不符。

> 两者对用户的影响差别很大：(a) 是静默降配，用户可能长期不知道；(b) 是显式失败，用户必须处理。

### 6.2 存量用户如何被告知？

评审文档 3.3.1 明确写了"升级前已配置 >60% 的用户**需修改内存比例或显式配置 dangerous_mode=true**"。
既然**要求用户改配置**，就属于**用户可感知的变更**。

- 评审文档说"**不需要更新用户手册**"、"使用人员：内部"
- 但**升级后写入内存下降**是用户能观测到的

**请确认**：发版说明是否需要增加一条"StorageEngine 占比超过 60% 会被限幅到 60%"的提示？
（不暴露 `dangerous_mode` 本身没问题，但"容量变化"这件事建议让用户知道。）

### 6.3 `dangerous_mode=true` 的开启方式与风险告知

参数"不对外暴露、仅在内部运维宝典中体现"。请确认：
- 具体开启方式（配置文件 / JMX / 其他）
- 开启后的风险告知方式
- 是否需要审计记录

### 6.4 限幅后的分配自洽性

限幅只压 StorageEngine 段，非 StorageEngine 段走 `calculateNonStorageMemorySize` 重新缩放
（涉及 `SAFE_STORAGE_ENGINE_MEMORY_DENOMINATOR - NUMERATOR = 2` 的系数）。请确认：
- 限幅后**五段内存之和是否仍 ≤ maxMemory**
- 各段之间的相对比例是否仍满足配置约束
- 是否会出现"某一段反而比限幅前更大"的情况

## 七、测试侧后续动作

MB-02 用例的 ② 段（`9:1:1:1:1:1` 期望 Write = maxMemory × 9/14 且**不限幅**）是**基于 2.0.12.1 的旧行为**，需要按新行为调整：

| 场景 | 配置建议 | 期望 |
|---|---|---|
| 不限幅 | storage 占比 **≤ 60%**（例如 `5:1:1:1:1:1` = 50%） | Write 按比例分配，**无**限幅告警 |
| 应限幅 | storage 占比 **> 60%**（例如 `9:1:1:1:1:1` = 64.3%） | Write = maxMemory × 60%，**有**限幅告警 |
| 风险模式 | 同上 + `dangerous_mode=true` | Write 按比例分配，**无**限幅告警 |
